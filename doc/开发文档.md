### 实现方法及技术原理

- 结构上只有一个「源码根」`src/`，页面与 Python 同处一个包，PyInstaller 的 `--add-data` 直接把 `src/www` 映射成
  包内 `www`，因此 `WEB` 在源码态与冻结态只差一个基准目录，不必再维护两套路径。
- uv 只管环境与依赖声明：项目运行时零第三方依赖，`uv.lock` 锁的是 dev 工具链（ruff/black/pyinstaller），
  保证「换台机器 `uv sync` 后 ruff、打包行为一致」。
- logging 用独立 logger + 单 handler，`propagate = False`，避免 root logger 重复输出；`say()` 保持原有的
  「只打印消息、不带级别/时间戳」外观，所以控制台横幅、地址提示的排版没有变化。

## 2026-11-13 · 修复：机会卡弹窗、电脑弹窗停留与电脑交接间隔

**机会卡没有弹窗**：原因和结算窗相同——前端把机会卡排在 `dur + 40ms`，而帧队列在 `dur`
就切下一帧，定时器触发时状态已经不是 `chance`，卡片被跳过；服务端电脑又只等 2 秒，
早于骰子 + 走格动画结束。

页面实际渲染有延迟（多人机局尤其明显）时，电脑会在弹窗刚出现不久就确认。

**修复**：
- 前端 `applyFrame()` 的机会卡定时器改为 `dur - 90ms` 触发，并只校验「当前仍是 chance
  且有 chance」，不再被下一帧抢掉；
- 新增 `settle_seen` / `chance_seen` 回报：弹窗真正画到屏幕上后，前端调用一次；
  服务端收到后，若当前是电脑，则取消兜底计时，改为从这一刻起**精确等待 2 秒**再自动确定；
- 没有客户端回报时保留兜底计时（动画 + 2 秒 + 2.5 秒余量），不会把局卡死；
- `BOT_DELAY["roll"]` 从 1.15 秒改为 2.0 秒：电脑结束回合后，下一位电脑掷骰前固定留 2 秒；

## 2026-11-13 · 修复：电脑结算窗还没出现就自动确认

**现象**：房租、起点工资、医院/税费、停车场奖金这些结算，轮到电脑时所有玩家都看不到确认窗；
日志里只有「等确认」和下一条已确认，回合已经交给下一位。

**根因**：前端 `applyFrame()` 要把骰子 2.6 秒 + 走格动画（每格 172ms）播完，才在 `dur + 60ms` 弹结算窗；
服务端电脑的 `_schedule_bot()` 却只等 `BOT_DELAY["settle"] = 2.0s` 就调 `settle_ok()`。
走 6 格时前端约 3.9 秒才弹窗，电脑 2 秒就确认并推进回合，弹窗永远来不及出现。

**修复**（`server.py`）：
- 掷骰后记录本回合结算窗前的动画时长 `settle_lead = 2.6 + 0.172 * steps + 0.16`；
- 电脑在 `settle` 阶段的自动确认延迟改为 `settle_lead + 2.0 + 0.2` 秒，即「弹窗出现后再停留 2 秒」；
- 第一次结算确认后把 `settle_lead` 清零；同一回合后续的租金等结算窗直接按 2 秒停留；
- 机会卡确认后也清零，避免把前面的掷骰动画时长重复计入；
- 载入存档、结束回合时重置，避免旧值影响下一回合。

**修复**（`web/index.html`）：
- 弹窗定时器原本在 `dur + 60ms` 触发，而帧队列在 `dur` 就切下一帧并把 `state` 换掉，
  定时器里的 `S.state === st` 判空直接失败，弹窗被吞。改为在帧结束前 `dur - 90ms` 触发，
  并只校验「当前仍是 settle 且有 settle」，不再比对帧对象身份。

**验证**：新增 `tests/test_settle_timing.py`，直接驱动 Game 计时器：
`lead=0` 时确认耗时 2.21s，`lead=3` 时 5.24s，均满足「lead + 2.2s」；`SETTLE TIMING PASS`。

## 2026-11-13 · 修复：多人载入同一存档后，后载入把前一个人的登录态冲掉

**现象**：两个玩家先后点「载入存档」并各认领一个座位，一个人行动后，另一个人变成「登录状态失效，请重新加入」，必须刷新再载入。

**根因**：`load_from_db()` 对**同一个 `game_id` 重复载入不拦**。第二个玩家点载入时会再跑一次 `restore()`，而 `restore()` 末尾无条件 `self.tokens = {}`，把第一个玩家已认领的 token 全清空；他下一次 `/api/action` 就被 `act()` 的 `pid_of(token) is None` 判成失效。

**修法**：`Game.load_from_db()` 在「别的局在进行」校验之后加一条幂等保护：
```python
if self.game_id == game_id and self.tokens:
    return self.seat_list()
```
同一局已载入且已有人认领时，只把当前座位表返回给后来者继续认领，不再 `restore`，不再清 token。首次载入、或还没人认领时仍走原来的恢复路径。

**回归**：
- 隔离服双人链路：`load1 → claim 甲 → load2 → claim 乙 → 甲 roll → 乙仍有效、甲仍有效`，输出 `BUGFIX OK`。
- `selftest.py` 末尾改为「restart 后载入 → 旧 token 失效（模拟重启）→ 认领 → 再载入同一档 → 先认领的人不掉线」，`ALL PASS`。
- 正式 9010 已用修复版重启（pid 46856）。

## 2026-11-13 · 第十六轮：先交易后掷骰、落地才结算、AI 落地后再决定、双方多选换地、整组恭喜

**需求**：① AI 改成「掷骰并走到落点之后」再决定这一回合做什么；② 租金、经过起点领钱、医院 / 税 / 停车场奖金都弹**所有玩家可见的确认窗**，
落点玩家点「确定」才动钱，电脑停 2 秒自动确认，走到不需要选择的地方不调接口；③ 回合流程改为「先交易再掷骰 → 落地执行（买地 / 升级 / 付租 / 抽卡，手动确定）→ 自动结束回合」；
④ 交易页双方地契都能多选；⑤ 集齐同色整组要有恭喜动画，地图租金后标「（已翻倍）」。

### 一、状态机：`action` 拆成 `settle` + `buy`

`phase` 现在只有 `lobby / setup / roll / settle / buy / chance / over`，原来的 `action` 删除。
- `roll`：只有掷骰前。交易只能在这个阶段、且 `current == pid` 时发起。
- `settle`：**待确认结算队列**。掷骰后先走格，把工资 / 租金 / 税费 / 奖金压进 `self.settles`，一条条弹窗，点一次 `settle_ok` 出队一条。
- `buy`：队列清空后，落点若是无主地或自己的地，进 `buy` 让玩家买 / 升；否则直接交棒。
- `chance`：机会卡待确认，`chance_ok` 后执行卡面。

`Game.reset` 新增 `self.settles = []`、`self.land = None`；`snapshot / restore` 一并带上，旧存档里的 `phase == "action"` 归一到 `"roll"` 并清 `pending`。

### 二、钱只在 `settle_ok` 里动

- `_move()` 只负责走格；经过起点时 `settles.append({"type":"salary", ...})`，**不直接加钱**。
- `_resolve()` 只判断落点并压队列：
  - 别人地 → `rent`（记业主 `to`）、税格 → `tax`（负数）、医院 → `tax`、停车场 → `park`、起点 / 休息 → 金额 0 的条目；
  - 无主地 / 自己的地 → `self.land = {"kind":"buy"|"own"}`；机会 → `self.land={"kind":"chance"}`；都不动钱。
- `_settle_start()`：队列非空发 `event("settle", pid, kind, tile, amount, to, text, name, icon)` 给全端，`phase="settle"`，日志写「等 XX 确认」；
  队列空就进 `_land_start()`。

  然后看队列是否还有下一条，没有就 `_land_start()`。
- `_land_start()`：`buy` → `pending` + `phase="buy"`；`own` → 满级 / 新买 / 钱不够则日志说明后 `_advance_turn()`，否则进 `buy` 升级；

## 2026-11-13 · 第十五轮：环境光修色（去掉绿底）+ AI 一回合只调一次接口

**需求**：① 上一轮的环境光在小狐（橙）回合里「四周橙、中心绿」，要修掉；四周渐变宽度固定不随窗口变，
光带调窄、不要碰到正文；② AI 每回合只调用一次接口，一次返回这回合要做的全部动作，程序拿到后按步骤执行。

### 一、中心为什么发绿

`body` 的底色原本是薄荷绿渐变（`#F3F8F5 → #EAF2EE → #E6EFEA`）。环境光层只在屏幕四边叠了玩家色，
中间那份绿底没被任何东西改过，于是出现「边缘橙、中间绿」的割裂 —— 看起来像环境光错色，其实是底色本身有颜色。
修法：把页面底色换成中性近白（`#F7F8F6 → #F2F4F2 → #EEF1EE`，右上角高光也去掉了绿），
环境色只由四边光带提供。实测中心日志卡像素 `(251,253,252)`、棋盘旁背景 `(252,254,253)`，不再带绿；
四边仍是玩家色（顶部 `(243,219,203)` 暖橙）。

同时把光带改成**固定 px 宽度**（不随窗口缩放）：桌面上下 92px / 左右 84px，alpha .26/.23/.22；
手机（`max-width: 899px`）54px / 40px，alpha .24/.21/.20。中心正文、日志、右侧面板完全在光带之外，
只有最外圈边距和最边上的一点地块卡片会被轻微提亮，文字对比度不受影响。
`box-shadow` 从 210px 收到 70px（手机 42px），只留一圈很薄的边缘余晖。

### 二、AI 改成「一回合一次计划」

旧实现是「每个阶段各问一次」：`buy` 问一次、`action` 问一次，AI 一回合要发 1–2 次请求，模型也看不见后半段，
经常出现「刚说想攒钱，下一句又买了」的割裂。

现在：

- **调用点只有一个**：`_bot_step()` 在 `phase == "roll"`（回合开头）把 AI 交给 `_run_ai_turn()`；
  `buy` / `action` 阶段如果本回合计划还在（`_ai_plan_valid()` 比对 `ai_plan_turn == turn_no`），
  直接 `_ai_plan_step()` 本地执行，**不再碰网络**。
- **计划形状**（`decide_plan()` + `_ai_plan_norm()`）：

```json
{"why":"一句话理由", "memory":"笔记",
 "buy":{"want":true,"maxPrice":300},
 "land":{"upgrade":true,"maxCost":200},
 "trade":{"target":"小雨","want":"码头","give":"小桥","giveCash":100}}
```

  `buy.want=false` = 踩到无主地一律放弃，`maxPrice` 是愿出的最高价；`land.upgrade=false` = 踩到自己的地也不升，
  `maxCost` 是愿付的最高升级费；`trade` 整块可省略，写了就在行动阶段发起并结束回合。
  也兼容简写：`"buy":"buy"` / `"land":"升级"` 会被归一化成对象。
- **结构校验与重试**：`_ai_plan_norm()` 检查 `want/upgrade` 必须是布尔、价格必须是非负数字、`trade` 至少要有 `want`；
  抛 `ValueError` 就把原因作为反馈塞回下一轮 prompt，最多 `AI_RETRY = 3` 次；三次不过或网络失败 → 日志
  「已交回人机接手」→ `ai_fail.log` 记 `phase = "plan"` 的原始返回 → `_local_step()` 用本地算法把这一回合走完。
- **执行期兜底**：`_ai_plan_step()` 里每一步都重新按当前局面判定（钱够不够、地还是不是他的、升级费超没超预算、
  是不是本回合刚买），走不通就 `pass_buy()` / `end_turn()` 保守收尾，不会把对局卡住。
- **只发一次调用**：原来笔记超长会再发一次「压缩笔记」请求（`fit_memory()`），本轮改成 `clamp_memory()` 就地截到 240 字，
  保证「一回合一次」是硬约束。
- **生命周期**：计划存在 `p["ai_plan"] / p["ai_plan_turn"]`，`_advance_turn()` 清空所有人旧计划；
  `restore()` 载入存档时也清掉，避免上一回合的计划被存档带进新回合。
- **思考态不变**：回合开头 `thinking = True` + `bump()`，前端照旧显示「AI 正在思考…」，只是从每回合 1–2 次变成 1 次。

## 2026-11-13 · 第十四轮：回合色改成环境光氛围 + 骰子定格停留 2 秒

**需求**：① 取消「整页盖一层当前玩家颜色的透明色布」，改成环境光 / 色相偏移的氛围感 —— 光影偏向目标玩家颜色，
而不是整屏蒙版；② 骰子转完要停 2 秒再消失。

### 一、旧方案的问题

第十一轮的做法是一片 `#turnTint` 纯色 + `mix-blend-mode: multiply` + `opacity 0.16`：颜色均匀铺满整屏，
白底、棋盘、面板一起被压成一层同色调，看起来就是「贴了张透明色纸」，没有任何方向感和光照明暗。

### 二、环境光方案

- `#turnTint` 退成容器（`position:fixed; inset:0; z-index:6; pointer-events:none; --tc: <RGB 三元组>`），
  里面放两个 `.tt-layer`，一前一后叠着；
- 每层不是纯色，而是**四束径向光 + 一圈内阴影**：上、下、左、右各一束从屏幕边缘射入，
  中心完全透明；再用 `box-shadow: inset 0 0 210px` 补一圈边缘余晖。
  参数：上/下 `100% 52% at 50% -12%/112%`（alpha .40/.38，40% 处收干净），
  左右 `56% 74% at -12%/112% 50%`（alpha .40）；
- `mix-blend-mode: soft-light`：只调明暗与色相，不做「换色」。中心留白仍是白底，
  棋盘上的色组颜色、角色头像色都不会被糊掉，页边则被当前玩家的灯照亮；
- 换人的过渡：渐变背景没法做 `background-color` 插值，所以改成**两层交叉淡变** —— `applyTurnTint()` 把新颜色写进
  当前没亮着的那一层（`--tc`），`.on` 淡入，旧层同步 `.off` 淡出，CSS `opacity 1.6s ease` 负责插值，
  换人时既连续又不跳色。`tintIdx` 记住现在亮的是哪一层；
- 收起：`phase == "over"`、当前玩家出局、切房间 / 认领 / 入场视图时两层一起 `.off`（`applyTurnTint(null)`）。
- 为什么不用 `filter: hue-rotate()`：它会把整页色相一起转，地产色组、玩家头像色全部偏移，
  认地就靠颜色，转色相等于把信息搞乱；软光只影响光的强弱，不动内容本身。

### 三、骰子定格 2 秒

- 相应地 `DICE_MS` 从 900 抬到 **2600**：`applyFrame()` 的 `landAt` / `runMove()` 都用它，
  所以「骰子消失 → 棋子起步」的顺序不变，不会出现骰子还占着屏幕、棋子已经走完一段。

## 2026-11-13 · 第十二轮：人机交换评估加入现金 / 回合 / 色组三个维度

**问题**：上一轮把门槛调高后，`bot_wants_trade()` 还是只看「两块地的静态估值差」——
同一笔交易，手头只剩 200 的电脑和手握 3000 的电脑给出一样的答案；第 3 回合和第 35 回合也一样；
「换回来就垄断」与「送出去让对手垄断」都只按一块地的单价算，看不出整组租金翻倍的连锁反应。

### 一、拆成三个可解释的小函数

- `_trade_safety(p)`：返回 `(安全垫, 缺钱程度 0..1)`。安全垫 = `keep × 局势姿态 + 最大租金 × risk`，
  `tight = 1 - min(1, money / (2 * 安全垫))`。缺钱越紧，现金权重越高。
- `_trade_tile_value(p, tile, role, progress, notes, other_id, costs)`：
  - `role="in"`（我拿到）：能凑齐我这组 → 先按 `1.15 + 0.35 × progress` 加成，再额外加上
    「同组我手上那些地 + 这块地」的租金和 × `(1 + 0.8 × progress)` —— 垄断是整组翻倍，不是这一块翻倍；
    组已被对手占死（对手 ≥ 总数-1 且我一块没有）→ 打 0.45 折；有 1~2 块同组 → 小幅加成。
  - `role="out"`（我让出）：让出后对手直接凑齐整组 → 按 `2.6 - 0.3 × progress` 倍重罚并记一条「代价」；
    对手在这组一块没有 → 打 0.75 折（他拿到也组不起来）。
- `bot_trade_eval(p, trade)` → `(是否接受, 一句理由)`：
  1. 现金差按缺钱程度加权：进账 × `(1 + 0.6 × tight)`，支出 × `(1 + 0.9 × tight)`；
  2. 掏完现金低于安全垫时：不是「凑齐整组」的交换直接拒（「换完手里太空」）；
  3. 门槛 `need = max(0.35/0.5/0.18 × 规模, 120)` 再乘 `(1 + 0.25 × progress + 0.2 × tight)`；
     规模取两块地里**较便宜**那块的分值，避免「两块大地相加」把门槛抬到不可能；
  4. 让对手凑整组的交易，即使净赚，也要 `现金补偿 ≥ 让出地块价值 × 1.2` 才点头；
  5. 结论附理由：赚了说「换回来就凑齐这组、整组租金翻倍（净赚约 X）」，亏了说「这笔我吃亏（-98）：这块让出去对方就凑齐整组，代价太大」。

### 二、把理由接进日志

`trade_answer()` 多一个可选 `reason` 参数，`say()` 时拼在「接受了交换 / 拒绝了交换」后面；

### 一、回合色调跟随当前玩家

### 一、日志默认「被顶下去」而不是「滚到底」

**根因**：日志列表是把整块中央区域 `innerHTML` 重建的，滚动位置只能在新节点**已挂进文档后**才设得住。
前一轮把 `scrollTop = 0` 写在 `renderCenter()` 里 —— 那会儿节点还没 `appendChild`，`scrollHeight` 是 0，

于是每帧都把列表拽到底部 —— 但列表是**倒序**的（最新在上），滚到底部等于看最旧的一条，想看到新日志还得往上滚。

**改法**（`web/index.html` → `renderBoard()`，删掉旧那句之后）：
- 记住 `S.logTop`（用户停留的滚动位置）与 `S.logHeight`（上一帧的 `scrollHeight`）；
- 默认 `S.logTop = 0` → 停顶部，新的一来就在最上面，旧的往下挤、滚出框外，视觉上「旧日志自然沉下去消失」；
- 只有玩家自己往下滚过（`logTop > 0`）才保留位置，并按 `新 scrollHeight - 旧 scrollHeight` 补偿，
  新条目在顶部插进来时视口不动，不会把人从正在读的历史里拽走；
- 监听 `scroll` 事件实时更新这两个值 —— 新节点每帧都会新建，所以监听也每帧挂一次，旧节点随之回收；

### 一、「退出房间再进来，角色已被选走」

**根因在前端**：`btnLeaveRoom` 里写的是 `api('/api/leave', {})`，而 `api()` 只负责拼 `fetch`、**不会自己加 token**；
服务端 `/api/leave` 是从 query 上取 `token` 的（`game.leave(token)`）。于是请求里的 token 是空串，
`leave()` 里 `pid = self.tokens.pop("", None)` 拿到 `None`，`if pid is not None` 这一整段跳过 ——
玩家既没被移出 `players`，角色也没释放，但页面这边照样 `clearToken()` 回入场页了。
下次再用同一个角色点「进入房间」，`join()` 的 `if char in self.used_chars()` 就把它拦下，报「这个角色已被选走」。

**修法**（一行）：`api('/api/leave?token=' + encodeURIComponent(S.token), {})`；
另外在前面加一句 `if (!S.token) { clearToken(); return; }`，token 丢了就直接回入场页，别发一个注定无效的请求。

服务端 `leave()` 本身的逻辑是对的（等待室阶段 `self.players.remove(p)`、顺手把房主转给下一个人），
所以这次没有改服务端 —— 之前误以为要回收座位，实际是请求里没带身份证。

> 注意：这次只修「点按钮退出」。**直接关掉页面 / 刷新**并不会调 `/api/leave`，座位仍然留着 ——
> 但因为 token 存在 `localStorage`，重新打开页面会自动回到原座位，不会再走 join，所以不会撞上这个报错。
> 只有换浏览器、清了缓存，或者别人用同一台机器时，才可能出现「角色被占」；那种情况请让原主人先点「退出房间」。

### 修掉的两个真 bug（都是「交换发起后没人应答」）

## 2026-11-12 · 第五轮：等待室「＋ AI」座位（服务端内置 AI 大脑，方案 A）

### 目标与取舍

要求：新增电脑时可选「人机」或「AI」；AI 走 OpenAI 兼容接口，配置放在同目录 `config.ini`；
并且四项增强——① 传给模型的不只是规则和局势，还带它自己总结的笔记（连贯决策、会记仇）；
② 笔记超长时由它自己精简；③ 模型返回先过规则校验，不合法重试，三次不行交回人机并把返回内容记 log；
④ 有「AI 正在思考…」显式等待态。

选了**方案 A：服务端内置 AI 大脑** —— AI 复用 `kind = "bot"` 的排拍（`_schedule_bot` / `threading.Timer`）
和全部规则入口（`buy` / `upgrade` / `end_turn`），只在「怎么想」上换成一次 HTTP 调用。
好处是：规则只有一份实现、AI 不可能作弊（它没有 token、也不直接写状态）、失败天然可降级到本地人机。
放弃了「整回合托管给模型」（一次返回整段动作，出错整回合作废、延迟全堆在前面）和「外部 Agent 走玩家 token」
（要第二个进程、防作弊弱）。

### 服务端

**配置**（`AI_CONFIG = ROOT / "config.ini"`，模板已随仓库提供）：

```ini
[ai]
enabled      = false                       ; 默认关，填好下面三行再改 true
base_url     = http://127.0.0.1:11434/v1   ; OpenAI / DeepSeek / 火山方舟 / 本地 ollama 都填这个形状
api_key      =                             ; 本地 ollama 可以留空
model        = qwen2.5:7b
timeout      = 8                           ; 每次调用的超时秒数，也是「正在思考」最多等多久
temperature  = 0.7
max_tokens   = 300

[ai.normal]                                ; 三档难度各一段人设，可只写 persona
model  = qwen2.5:7b
persona = 普通：该省就省
```

`AIBrain.reload()` 在启动时读一次；`ok = False` 时把原因写进 `reason`（例如「还没填 base_url」），
`view().settings.ai` 会带出去，前端据此把「＋ AI」按钮置灰并在下面写清差什么。运行期不再重读，
改配置要重启服务端（和棋盘常量一个规矩）。

**`AIBrain`**（放在 `bot_keep()` 之后、`class Game:` 之前）：

- `_chat(messages)`：`urllib.request` POST `<base_url>/chat/completions`，`Authorization: Bearer <api_key>`，
  取 `choices[0].message.content`；超时 / HTTP 错误 / JSON 解析失败统一抛 `RuntimeError`，由上层归成 `kind = "net"`。
- `_system_prompt(phase, persona)`：只给**当阶段合法的两个 action 值**（买地阶段 `buy`/`pass`，行动阶段 `upgrade`/`end`）。
  第一版把两个阶段的取值都写进「输出要求」，模型在行动阶段填了 `pass` —— 提示词里出现过期的选项就是隐患，现已收敛。
- `decide(phase, persona, context, memory)` → `(intent, err, kind)`；`extract_json(text)` 负责剥 ``` 围栏、
  取最外层 `{…}`，所以模型多说了两句废话也能救回来。
- `fit_memory(text)`：超过 `AI_MEM_HARD = 360` 字时单独发一次「压到 120 字以内」的调用；压不动就硬截到
  `AI_MEM_LIMIT = 240`。

**`Game` 侧**：

- `add_bot(level, brain="local")`：`brain == "ai"` 且 `ai_brain.ok` 为假时抛
  「AI 还没配好：<原因>，请检查 config.ini」，所以配置没填好时点「＋ AI」只是拿到一句人话，不会加出个废座位。
- 玩家多三个字段：`brain`（`local` / `ai`）、`memory`（它自己的笔记）、`thinking`（是否正在等模型）。
  `restore()` 补齐前两个默认值并**强制把 `thinking` 清成 False**（存档里可能存着一个「假思考」）。
- `_schedule_bot()` 在 `cur["thinking"]` 时直接 return —— 没有这条，思考期间每一帧 `bump()` 都会重排同一拍的
  `_bot_step`，模型会被连着叫好几次。AI 座位在 buy / action 阶段额外 +0.4s，让「正在思考」这一帧至少被打出来一次。
- `_bot_step()` 拆成两段：锁内判断（`_ai_alive`）→ 锁外干活。AI 走 `_run_ai_step()`，其余走 `_local_step()`
  （就是原来的启发式逻辑原封不动搬过去）。
- `_run_ai_step(pid, phase, turn_no)`：`thinking = True` + `bump()` → 最多 `AI_RETRY = 3` 轮
  （锁内 `_ai_context()` → 锁外 `decide()` → 锁外 `fit_memory()` → 锁内 `say(why, kind="ai")` + `_ai_apply()`），
  `_ai_apply` 抛 `ValueError` 就把原因做成 feedback 塞进下一轮 → 成功 return；
  三次都不行或 `kind == "net"` → 日志「已交回人机接手」+ `_log_ai_fail()` + `_local_step()`；`finally` 里 `_clear_thinking()`。
- **HTTP 一定在锁外**：一次模型调用就是 1–8 秒，持着 `Game.lock` 调它，整个对局（别人的 `/api/state` 也在等这把锁）都得等。
- `_ai_alive(pid, phase, turn_no)` 用 `phase` + `current` + `turn_no` + `frozen is None` 判断，**故意不看 `version`**：
  思考帧自己就会 `version += 1`，带 version 就永远判失败。
- `_ai_context()` 的内容：第几回合 / 场上人数 → 自己的现金与地契数 → 自己每块地的名字、等级、租金，
  以及「已满级 / 刚买本轮不能升 / 要走到它上面才能升 / 正踩着可花 X 升到 Y 租金」→ 对手的名字、现金、地契数、最贵租金 →
  场上最贵租金 → 本步两个选项的代价 → 自己的笔记 → 最近 10 条与它相关的流水 → 要求输出的 JSON 形状。
- `_log_ai_fail()` 写 `AI_FAIL_LOG = ROOT / "ai_fail.log"`，一行一条 JSON：
  `time / game / pid / name / level / model / phase / returned（模型原话，截 300 字）/ reason`。
  这条就是「后续做软件优化」的依据：调提示词前先看它到底回了什么。
- `view()` 新增 `players[].brain / thinking / note`（`note` 是笔记前 80 字）与 `settings.ai`
  （`ok / reason / model / timeout / retry`）；`act()` 的 `bot_add` 透传 `payload["brain"]`。
- `rules_payload()`「电脑玩家」一节改写：电脑分人机 / AI 两种、AI 有笔记和最近流水所以更连贯也记仇、
  动作先过校验不合法重来三次、思考时显示「AI 正在思考…」最多等几秒。

### 踩坑记录

1. **`props_of()` 返回的是地块下标（`list[int]`），不是地块字典**。第一版 `_ai_context()` 直接
   `upgrade_cost(t)` → `AttributeError: 'int' object has no attribute 'get'`，AI 决策全线抛异常退化成降级。
   已改成 `mine = [self.board[i] for i in self.props_of(pi)]`，对手那段同理。
2. **`subprocess.PIPE` 不消费会阻塞服务端**：自测脚本一开始把服务端 stdout 接成 PIPE 又不读，
   缓冲塞满后服务端线程卡在 `print` 上、持着锁不放手 → 客户端 `/api/state` 8 秒超时，看着像"AI 卡死"。
   改成重定向到 `srv.log` 后立刻正常。以后跑服务端一律写文件再读尾部。
3. **提示词里不能出现当阶段非法的选项**：见上面 `_system_prompt` 那条。
4. **`say(why)` 必须在 `_ai_apply()` 之前**：`_ai_apply` 内部会 `bump()` 推帧，写在后面的话会掉到下一帧，
   看起来像「AI 在下一个玩家的回合里插话」。
5. **`_schedule_bot` 不判 `thinking` 会重复排拍**：同一 phase 被反复重排，一次决策叫 N 次模型。

## 2026-11-12 · 第四轮：升级新规落实到界面 + 人机算法重做 + 规则说明

### 规则（服务端其实早已按新规实现，本轮把它讲到明面上）

升级的硬条件在 `Game.upgrade()` 里依次校验，任何一条不成立都抛 `ValueError`：

1. 轮到你、且处在「行动」阶段（`_need(pid, "action")`）；
2. 这块地是 `prop` 且 `owner == 你`；
3. **你正踩在这块地上**（`p["pos"] != tile["i"]` → 报错「只能升级自己正踩着的这块地」）；
4. **不是本回合刚买的**（`tile["bought_turn"] == self.turn_no` → 报错「下一回合再走到它上面才能升」）；
5. 没满级（`upgrade_cost` 不为 `None`）、金币够升级费。

`buy()` 与交换成交都会写 `bought_turn = turn_no`，所以「刚拿到的地」本回合一律升不了；
`turn_no` 在 `start()` 置 1、`_advance_turn()` 自增，快照/恢复都带它。

### 本轮改动

- **界面把「为什么升不了」说清楚**：`view()` 的每块 prop 多下发 `upWhy`（`已满级` / `刚买·下轮可升` /
  `没走到这儿` / `钱不够`）；侧栏地契行按它显示对应灰字，只有「站在自己的地上 + 不是刚买 + 钱够」才出现可点的
  「升级 X」按钮。提示条也分四种说法（站在自己地上可升级 / 刚买 / 已满级 / 脚下不是你的地）。
- **点棋盘看详情**时，如果那块地是自己的但没站上去，补一句「要走到这块地上才能升级」。
- **规则说明**：`/api/rules` 的内容全部由常量算出（等级倍率、升级费率、税费、上限），新增一节
  「为什么升级按钮是灰的？」逐条解释四种灰字；入场页、等待室、对局页（玩家侧栏）都能点开同一个弹窗，
  观战者也能看。
- **人机算法重做**：
  - 升级判定从「租金增量 ≥ 升级费 × value」换成**回收期**：`payback = 升级费 ÷ 每次多收的租金`，
    难度阈值 3.3 / 3.0 / 3.8（整组在手放宽 15%）。旧门槛下 `gain`（20–60）几乎过不了 `cost × 0.25~0.33`，
    电脑整整 110 秒只升了 1 次。
  - 新增**资金姿态** `_bot_pace()`：现金 ≥ 同场平均 1.7 倍就收紧（keep 打 6 折），≤ 0.65 倍就放开
    （keep 打 1.3 倍），所以同一档难度也会随局势变化，而不是一路同一套参数。
  - 升级的安全垫从「最贵租金 × risk × 0.5」放宽到 × 0.35，避免电脑攒着钱一次都不升；
    三档的「非整组也升」概率调到 0.85 / 0.6 / 0.95。
  - 其他（买地凑色组、留钱、交换估值、只应答不主动）保持不变。
- **前端队列容错**：`pumpFrames()` 给 `applyFrame()` 套了 `try/catch`。之前某帧渲染抛错会把 `frameBusy`
  永久卡住，整页面停在那一帧（本次联调就触发过一次：地契行引用了未定义的变量）。现在单帧出错只记日志，
  队列继续往下播。

## 2026-11-12 · 第三轮补充：人机节奏与动画排队（修复「多台电脑连着动、看不清」）

### 问题

加了多台电脑后，观战/真人几乎看不到过程：骰子不滚、棋子一眼瞬移到终点、买地卡一闪就被下一张盖掉，
多台电脑像同时在动。分成两个原因：

1. **服务端间隔太短**：`BOT_DELAY` 只有 0.85 / 1.15 / 0.7 秒，而一次「掷骰 + 逐格移动」的动画本身要 1.5–3 秒，
   下一帧必然压在上面的动画上。
2. **前端把动画打断了**：`applyState()` 里只要 `S.animating` 为真就直接把棋子挪到终点、`moves = []`，
   骰子还没落地、棋子还没走就跳到结果；`pushPop()` 每次清空卡片层，卡片被后一张替换。
3. **一次状态变化只推一条事件**：`self.news` 是单值，`roll()` 里 `event("dice")` 之后 `_resolve` 又 `event("land")`，
   前者被覆盖 —— 前端只收到 `land`（`case 'land': break` 什么都不做），所以骰子动画从来没播过。

### 改动内容

- **服务端事件批**：新增 `self.news_frame`（本帧累积）与 `self.news_pub`（已推出的那一批）；
  `event()` 同时追加到 frame；`bump()` 里 `news_pub = frame` 再清空；`view()` 多下发 `newsList`（按 seq 升序的数组），
  `news` 保留为最后一条以兼容。一次「掷骰 + 领工资 + 落地 + 抽卡」现在能完整播完。
- **服务端节奏**：`BOT_DELAY = {roll: 1.15, buy: 2.0, action: 1.5}`，并新增
  `BOT_MOVE_LEAD = 1.1` / `BOT_STEP_ANIM = 0.17`：掷完骰子的那一帧，接下来的买地 / 行动决策要等
  `max(基础间隔, 1.1 + 0.17 × 步数)`，也就是「骰子 + 逐格移动」播完才继续。`self.last_steps` 记本回合步数，
  `_advance_turn()` / `reset()` 清零。
- **前端状态帧队列**：`applyState()` 只负责入队（`frameQueue`，超过 8 帧丢旧留新），`pumpFrames()` 串行取帧，
  `applyFrame()` 返回这一帧动画要占的时长（`骰子 0.9s + Σ(步数×0.172 + 0.12)`），播完才上下一帧，
  所以连续多帧不会互相打断；房间/暂停视图仍然即时生效（清空队列）。
- **前端多事件播放**：`applyFrame()` 取 `newsList` 中 `seq > S.lastNews` 的事件，按顺序播，
  `handleNews()` 增加 `at` 偏移参数（骰子之后的事件统一延后 `DICE_MS = 900ms` 再演），飘字 / 闪光 / 卡片都跟着延后，
  不再挤在同一瞬间。
- **观战提示**：观战者右侧主按钮文案从「掷骰子」改成「观战中」，避免看着像能点。

### 测试情况

- `python selftest.py 9010`：ALL PASS（协议只多下发 `newsList`，逻辑没动）。
- 服务端节奏实测（4 台电脑、轮询 20ms 记录版本变化）：帧间隔 1.17s（轮到某人掷骰）/
  2.1–2.3s（掷骰 → 买地决策）/ 2.1s（买地 → 下一位），一圈约 11 秒。
- 浏览器实测（无头 Chrome 采样 90ms、12 秒）：骰子滚动动画出现 15 帧（≈2 次完整滚动）、
  记录到 3 张不同的「地契到手」卡片（码头 / 老屋 / 茶铺）而不再互相覆盖、棋子位置出现逐格中间帧；
  截图确认「买地阶段 阿呆 正在决定买不买」的停顿、卡片完整展示、观战面板只读。

### 待办 / 已知限制

- 前端队列会给画面带来最多一帧（约 1–3 秒）的滞后，这是「看清动画」的代价；8 帧以上的积压会丢旧帧直接跟上。
- 骰子动画与棋子起步是前后衔接（不重叠），4 台电脑一轮约 11 秒，人少时节奏更快。

## 2026-11-12 · 第三轮：等待室设置 + 暂停回开始页 + 地块三级 + 人机（方案 A）+ 观战

- **房主身份从 `pid` 换成 token**：新增 `self.host_token`，`is_admin(token)` 一处判定，`act()` 里用

- **暂停不新增视图**：`snapshot()` 会 `pop("frozen")` 防止无限嵌套；`persist()` 的跳过条件仍是 `phase == "lobby"`，
  所以 `"setup"` 会正常落库 —— 重新载入一个「暂停中的局」会直接回到暂停状态的开始页。

- **交易表态排程**：`trade` 结构里加 `asked` 标记，`_schedule_bot()` 先扫「有未表态且对方是电脑」的交易排 `_bot_trade_step()`，

- **续跑定时器**：`Timer` 回调里重入 `with self.lock` 安全，因为 `threading.Condition()` 默认基于 `RLock`。

### 实现方法及技术原理

- 状态仍然只有一个 `Game`，暂停就是「把状态拍成快照移出去，把 `phase` 拨回 `setup`」，没有第二套数据源；
  因此暂停期间所有 `act()` 入口天然被 `phase` 判定挡住（掷骰、买地、结束回合都不在 `setup` 的合法相位里）。
- 电脑玩家和真人共享同一套规则函数（`roll / buy / upgrade / end_turn`），只是驱动者是定时器而不是 HTTP 请求；
  这是选方案 A 的核心收益：不复制规则、不引入第二条通信链路、4 台电脑也只是 4 个 `kind == "bot"` 的玩家。
- 定时器用「版本号 + 当前行动者 + 阶段」三元组做乐观校验，任何一次 `bump()` 都会重排 Timer，
  所以暂停、继续、重开、真人抢先操作都不会出现两个定时器同时推进同一台电脑。
- 升级只改 `tile.level` 一个字段，租金在结算时由 `rent_at()` 现算，`view()` 再把 `rentNow / upCost` 一起下发，
  保证「棋盘上写的租金」和「真正扣的钱」是同一个函数算出来的。

### 待办 / 已知限制

- 电脑不会主动发起交换（这是本轮的产品决定），也不会做「几家联合压一家」这类策略；难度只影响买地 / 升级 / 受理交换的倾向。
- 只支持单桌、单活动局；4 台电脑也必须由真人（观战）点一下「开始」。
- 暂停中的局会写进存档，但存档列表里只标 `playing`，没有单独的「已暂停」状态标签。
- 存档仍无删除 / 重命名入口；清历史只能停服后删 `monopoly.db`。

## 2026-11-12 · 第二轮：本地数据库存档 + 地块底色分色 + 金币旁显示地契数

### 改动内容

1. **本地存档（方案 B：多存档位 / 认领座位 / 只存当前局面 / 单活动局）**
   - 新增 SQLite 存档层，库文件固定为 `server.py` 同目录的 `monopoly.db`（WAL 模式、`sqlite3.Row`）；
   - 表：`meta(key, value)` 存 `schema_version`，`games(id, title, created_at, updated_at, status, phase, summary, snapshot)`；
   - 每走一步自动落库；重启服务端后仍在；入场页可「新游戏」或「载入存档」；
   - 载入后 token 全部作废，各人从「认领座位」页重新拿凭证，座位被别人点走就坐不上。
2. **非可买地块分色**：起点 / 机会（含幸运角）/ 税（税务局、市政税）/ 医院 / 停车场 / 休息站六类各给一组
   底色 + 描边 + 图标色，替换原来统一的 `.tile.special` 白底，并给可买地块保留色组色带，两者一眼能分。
3. **金币旁显示地契数量**：「我的卡片」「中央玩家条」「右侧玩家列表」三处都改成「金币 + N 契」，
   数据直接用 `view()` 里已有的 `player.props`（地契索引数组）长度，不动接口。
4. **接口新增**：`GET /api/saves`、`GET /api/seats`、`POST /api/load`、`POST /api/claim`。
5. **自测扩展**：`selftest.py` 末尾加存档链路（列表 → 载入 → 旧 token 失效 → 认领 → 金币地契一致 → 重复认领被拒）。

### 实现要点

- `DB_PATH = ROOT / "monopoly.db"`、`SCHEMA_VERSION = "1"`；`db_open()` 每次开新连接（`timeout=8`、`PRAGMA journal_mode=WAL`），
  多线程下不共享连接，避免锁跨线程问题。
- `Game` 增加 `self.game_id`（未开局为 `None`）与 `self.db_ok`；`snapshot()` 导出 `players / board / phase / current / host /
  dice / pending / log / news / trades / winner / version`，**不含 `tokens`**；`restore(snap, game_id)` 整份灌回、
  清空 `tokens`、`version` 置为快照值 +1 并 `notify_all()`。
- 落库挂在 `bump()` 里：`persist()` 在 `phase == "lobby"`、`game_id is None` 或 `db_ok == False` 时直接返回；
  写失败打印一次后置 `db_ok = False`，整局降级为纯内存，不阻断游戏。因为所有改状态的公开方法最后都调 `bump()`，天然做到「一步一存」。
- 一局一行：`start()` 里 `db_new_game()` 插入（标题「阿明、小雨 的局」），之后 `UPDATE` 同一行；
  `phase == "over"` 时 `status = "over"`；`restart()` 先把旧行封存为 `over`，再 `game_id = None`，下一局另插一行。
- `claim_seat(pid)`：`phase == "lobby"` 拒绝；座位不存在拒绝；`pid in tokens.values()` 拒绝「这个座位已经有人坐下了」；
  否则发新 token、写一条 `kind="join"` 日志并 `bump()`。
- `load_from_db(gid)`：内存里 `phase != "lobby"` 且 `game_id != gid` 时 409「现在还有一局在进行」；
  读 `snapshot` 为空则报「这局还没开始过」。
- 前端 `TINTS` 按 `type` 给 `go / chance / tax / hospital / park / rest` 六组色（薄荷绿 / 暖黄 / 浅砖红 / 浅蓝 / 青绿 / 浅紫），
  同时写 `--ico` 让 `.tile.special .ticon` 用对应的深色；可买地块仍由色组色带 + 业主染色决定背景。

### 实现方法及技术原理

- 存档只存「当前局面」，不存事件流水：状态本来就集中在 `Game` 的十几个字段里，`snapshot()` / `restore()` 一对一映射即可，
  恢复出来的棋盘、地契、日志、`pending` 买地阶段和原局完全相同，代价是不能回放到某一步。
- token 不落库是刻意设计：token 是运行期登录凭证，写进磁盘等于把会话凭据留在文件里；载入时清空并按需重新签发，
  同时用「一个 pid 只允许一个 token」保证座位独占。
- 「单活动局」在 `load_from_db()` 一处收口：内存 `phase != "lobby"` 时只允许重新载入当前这局，别的存档一律 409。
- 降级策略：数据库打不开 / 写失败只影响存档，不影响对局（`db_ok = False` 后 `persist()` 直接返回）。
- 地块分色靠「类型 → 底色」的静态表 + 渲染时写 CSS 变量，不引入新接口；地契数直接取 `player.props.length`，
  所以协议零改动。

### 待办 / 已知限制

- 存档没有删除 / 重命名入口，历史局只能靠手动删 `monopoly.db` 清空。
- 不做身份延续：换设备载入后，原设备若还开着会继续持有旧 token，直到重启服务端（同一座位因此只会被一个 token 占住，不会串号）。
- 仍不支持多桌并行、观战、踢人；`summary` 只做列表展示，没有统计（胜率、总资产曲线等）。
- 服务端日志仍是 `print`，未切到 `logging`（历史遗留，本轮未重构）。
- PowerShell 下链式命令的中文 stdout 偶发丢失，压测/验收脚本统一 `*>` 重定向到 `%TEMP%` 文件再读。

### 实现方法及技术原理

- 服务端只做状态与规则：`Game` 持全部状态，`lock` 内改状态 + `version += 1` + `notify_all()`；SSE 线程按 `version` 变化推帧。

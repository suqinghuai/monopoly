# 联机大厅 + 多房间 + 桌游选择 · 改造方案

> 状态：**方案评审中，未改任何代码**
> 编写时间：2026-11-14
> 适用版本：当前 `src/server.py`（2913 行）+ `src/www/index.html`（3407 行）这一版

---

## 0. 一句话结论

把「一个进程只能开一桌」改成「一个进程维护多张桌子」，入口从「大富翁入场页」抬升为「联机大厅」，
并把「等待室」升级成「准备室」——准备室里可以选桌游（大富翁是其中一款），选完再对着那张桌子准备、开局。

改造分 6 步走（P0 结构 → P1 房间层 → P2 大厅与准备室 → P3 桌游抽象 → P4 存档与生命周期 → P5 安卓对齐）。
**先做 P0 的纯搬迁**，保证在不懂业务细节的情况下也能回归验证，再叠加房间层。

## 1. 现状盘点（改造的直接约束）

| 位置 | 现状 | 对改造的影响 |
| --- | --- | --- |
| `src/server.py` 2913 行 | 模块级单例 `game = Game()`；`Game.lock` 是 `threading.Condition`；改状态后 `version += 1` + `notify_all()` | 必须引入房间容器，锁与版本号降级到「每房间一份」 |

要点：
- **座位即角色**：大富翁的点位格子里就显示棋子头像，点空位入座，等价于原来的「选角色 + 加入」。别的桌游用通用头像，接口一致。
- **准备状态**：非房主必须点「准备」，房主默认已准备；全员准备后房主才能「开始游戏」（房主可强制开始，按钮旁标「1 人未准备」）。

- 邀请链接形如 `https://…/?room=K7F2QX`，打开后自动跳准备室（未登录先填昵称）。

### 2.3 对局 / 结算

沿用现有 `#game`，把棋盘与面板包成「桌游视图容器」：容器只负责挂载/卸载和状态帧分发，具体棋盘、骰子、卡片、日志、面板全部留在大富翁模块里，现有动画与节奏逻辑一行不改。

## 3. 关键设计决策

### D1 多房间模型：一进程多桌，每桌一把锁

```
RoomManager（全局单例，一把 manager.lock 只保护 rooms 字典）
└── Room × N（每间一把 threading.Condition + 自己的 version）
    ├── code / name / password / created_at / idle 计时
    ├── game_id + game 实例（当前只有 monopoly）
    ├── members: {token: {name, seat, ready, joined_at, last_seen}}
    ├── watchers: set[token]
    └── status: waiting | playing | paused | over
```

- **锁顺序固定**：先 `manager.lock`，再 `room.lock`，绝不反向；`manager.lock` 内不做任何耗时操作（不写库、不发 HTTP、不 join 线程）。
- **版本号**：`Room.version` 是唯一计数器，房间内任何变化（入座、准备、换桌游、游戏推进）都 `+1` 并 `notify_all()`。大富翁的 `bump()` 改成调 `room.bump()`，`Game.version` 变成指向 `room.version` 的只读属性——这样 2900 行游戏代码的动线完全不变。
- **并发上限**：`MAX_ROOMS = 20`、单 token 最多同时 3 间房；每房间人数由桌游 `max_players` 决定（大富翁 4）。超限直接 409 并在大厅提示，不排队。

### D2 身份分层：会话 token（大厅） → 座位（房间）

- `POST /api/session {name}`：首次进站发 `token`（`secrets.token_hex(14)`），存 `localStorage["tb.token"]` 并同步到 URL `?token=`（沿用现在的断线重连手法）。改昵称不换 token。
- 进房时把 token 登记到该房间的 `members`；座位是房间内概念（`seat` = 大富翁的 pid 或别的桌游的座位号）。
- 「只观战」= 进 `watchers`，不占座，仍能看直播与日志。
- 一个 token 可以同时在 A 房坐着、在 B 房观战——服务端按 `(room, token)` 索引，推送线程按房间区分；跨房操作一律 403。

### D3 房间码 + 可选密码

- 房间码 6 位，Base32 字符集去掉易混的 `0/O/1/I`（`K7F2QX` 这类），大小写不敏感，生成时查重。
- 密码可选（4 位数字），存 `sha256(salt + pwd)`；密码只挡进房，不挡观战（房主可设「观战需密码」后续再说，本期不做）。
- 房间码是唯一主键，所有房间级接口都用它：`/api/rooms/K7F2QX/...`。

### D4 桌游注册表（服务端 / 前端各一份，元数据一致）

服务端：`GAME_META = {id, name, tagline, min_players, max_players, supports_bots, available, accent}`

| id | 名称 | 状态 | 说明 |
| --- | --- | --- | --- |
| `monopoly` | 大富翁 | available | 现有 Game 逻辑整体迁入 |
| `catan` | 卡坦岛 | 敬请期待 | 只在准备室与大厅过滤器里露脸，不可选 |
| `uno` | UNO | 敬请期待 | 同上 |

大厅按 `available` 分页签；准备室里不可用的桌游卡片置灰 + 「敬请期待」，点不动（不做假入口）。

**桌游插件接口（服务端）**：一个 duck-type 类，房间按需实例化：

```python
class GameBase:
    GAME_ID / GAME_NAME / MIN_PLAYERS / MAX_PLAYERS
    def __init__(self, room): ...                 # 拿 room.lock / room.tokens / room.watchers
    def settings_schema(self) -> dict: ...        # 准备室表单（字段、默认值、可选值、锁定条件）
    def seat_options(self) -> list[dict]: ...     # 角色池 / 空位定义
    def view(self, pid, token) -> dict: ...       # 整帧状态（沿用现有协议，前端几乎零改动）
    def act(self, token, action, payload) -> None: ...
    def snapshot(self) / restore(self, snap): ...
    def status(self) -> str: ...                  # 映射 waiting / playing / paused / over
```

大富翁的 `Game` 只需：①把 `__init__` 从「自建 lock」改成「接 room 的 lock/tokens/watchers」；②`bump()` 转发给 room；③`act()` 里新增 `ready`/`char` 等房间级动作交给 Room 处理。其余（掷骰、结算确认、电脑定时器、AI 计划、换地评估、存档）**一行不动**。

### D5 推送：两个频道，一个连接

- `GET /ws?scope=lobby`：大厅频道，推 `rooms 列表 + games + 在线人数`（变化即推，帧很小）。
- `GET /ws?room=K7F2QX&token=…`：房间频道，推该玩家的 `room + game.view()` 整帧（与现在完全同形）。
- 兜底照旧：WS 握手失败 → `GET /api/events?scope=lobby` / `?room=…&token=…` → 轮询 `GET /api/lobby`（5s）/ `GET /api/rooms/:code/state`（2s）。
- 页面切换视图时**先关旧连接再开新连接**，避免一个页面挂两条长连接；`wakeUp()`（回前台/上线）逻辑保留。

### D6 房间生命周期与回收（必须有，否则内存会漏）

| 场景 | 规则 |
| --- | --- |
| 房主退出（等待中） | 房主顺延给下一位真人；最后一人退出 → 立即解散 |
| 房主退出（对局中） | 座位保留（现有「局中不能退座」规则不变），房主顺延；无人可顺延时房间进入「托管」状态，暂停等回来 |
| 全员掉线（等待中） | 10 分钟后自动解散（`IDLE_WAITING = 600s`） |
| 全员掉线（对局中） | 30 分钟后冻结收档并解散（`IDLE_PLAYING = 1800s`），局面已 `persist()` 落库，可从存档续 |
| 已结束（over） | 保留 10 分钟可看结局，然后解散；存档保留 |
| 服务端重启 | 房间全部清空（房间是运行态）；进行中的局已在存档里，玩家从准备室「载入存档」续玩——行为等价于现在重启后载入存档 |
| 回收线程 | 单线程 `threading.Thread(daemon=True)`，每 30s 扫一遍，顺手取消所有 bot 定时器 |

### D7 存档：加 `game_type`，槽位按桌游分开

- `SCHEMA_VERSION` 提到 `"2"`，迁移方式：`ALTER TABLE games ADD COLUMN game_type TEXT NOT NULL DEFAULT 'monopoly'`（旧行自动归大富翁）。
- `SAVE_SLOTS = 6` 改成「每种桌游各留 6 局」，`db_prune_games` 按 `game_type` 分组裁剪。
- 去掉 `load_from_db()` 的「另一局在进行就拒绝」互斥：现在允许多局并行，载入存档改为**在准备室里发起**，把快照恢复进当前房间（房间内若已开局则拒绝，409）。
- 载入后仍走「认领座位」流程（`#claimView` 保留，逻辑不变）。

### D8 前端结构：拆文件，但不上构建工具

保持零依赖、零打包，用经典 `<script defer>` 按顺序引入（不用 ES Module，避开 Android WebView / `file://` 的模块加载坑）：

### 4.1 目录与模块拆分

│   ├── store.py              # SQLite：schema v2、games 增列、按类型裁剪

**房间**

| 方法 | 路径 | 说明 |

| `POST` | `/api/rooms` | `{game, name?, password?, private?}` → `{room, token}`；建房即入座房主位 |
| `POST` | `/api/rooms/:code/join` | `{password?, spectator?}` → `{room}` |
| `POST` | `/api/rooms/:code/leave` | 退房；局中玩家退座仍拒绝（沿用旧规则） |
| `GET` | `/api/rooms/:code` | 房间摘要（准备室轮询兜底） |
| `POST` | `/api/rooms/:code/ready` | `{ready}` |
| `POST` | `/api/rooms/:code/seat` | `{seat, char?}` 入座 / 换座位 / 换角色 |
| `POST` | `/api/rooms/:code/game` | `{game}` 换桌游（仅等待中、仅房主） |
| `POST` | `/api/rooms/:code/host` | `{token}` 移交房主 |
| `POST` | `/api/rooms/:code/kick` | `{token}` 请出（仅房主） |
| `POST` | `/api/rooms/:code/close` | 解散（仅房主） |
| `POST` | `/api/rooms/:code/load` | `{saveId}` 载入存档到本房（仅等待中） |
| `GET` | `/api/rooms/:code/state?token=` | 整帧（`room` + `game.view`） |
| `GET` | `/ws?room=:code&token=` / `/api/events?room=:code&token=` | 房间实时频道 |
| `POST` | `/api/rooms/:code/action?token=` | 游戏动作（`roll/settle_ok/buy/…`，原 `/api/action` 原样迁入） |
| `POST` | `/api/rooms/:code/chat?token=` | 房内聊天（原逻辑） |
| `GET` | `/api/rooms/:code/seats` | 座位认领表（原 `/api/seats`） |
| `POST` | `/api/rooms/:code/claim` | 认领存档座位（原 `/api/claim`） |
| `GET` | `/api/saves?game=monopoly` | 存档列表（按类型） |
| `GET/POST` | `/api/ai_config` | 全局 AI 配置（不变） |

**兼容策略**：旧的无房间路径（`/api/state`、`/api/action` 等）**不保留**。理由：页面与服务端同包发布（exe / APK 都自带页面），旧接口只会带来「两套语义」的维护负担。老用户手里的 `?token=` 失效后就回到大厅（前端已能处理「登录状态失效」这一错误码）。

### 4.3 并发与定时器（最容易出问题的两块）

- **电脑定时器**：`threading.Timer` 现在挂在 `Game` 上。改造后每房间都有，必须在 `Room.close()` / 回收时 `cancel()` 所有未触发的 timer，并让 `_bot_step()` 的版本三元组校验继续生效（现有机制已经防「两个 timer 推同一台电脑」，多房间下天然隔离，不用重写）。
- **AI 请求**：`AIBrain._chat` 在锁外发 HTTP。多房间会出现「并发请求同一端点」，建议加一个全局 `threading.Semaphore(2)` 限流 + 现有超时/重试不变，避免多开房间把接口打挂。
- **SQLite 写入**：现在 `bump()` 里同步写库。多房间会争用写锁，措施：`PRAGMA journal_mode=WAL` + `timeout=5s`，并把 `persist()` 改成「每房间最多 5 秒写一次」的节流（关键节点仍立即写：开局、结束、暂停）。
- **推送线程数**：`ThreadingHTTPServer` 一连接一线程，20 间房 × 4 人 + 观战 ≈ 100 线程，量级可接受；超过就调 `MAX_ROOMS`，不做多进程。

## 11. 明确不做（本方案边界）

- 不做账号体系（注册 / 密码找回 / 跨设备同步）；身份就是本机 token + 昵称。
- 不做匹配大厅、自动开局、排行榜、战绩、观战回放。
- 不做多进程 / 多机集群；一台机器一个进程，房间数上限 20。
- 不做公网反滥用（限流、风控、验证码）；只有房间密码 + 建房上限。
- 不改大富翁的任何规则、数值、电脑与 AI 策略（改造只碰「容器」，不碰「玩法」）。
- 不做房间内语音 / 视频。
